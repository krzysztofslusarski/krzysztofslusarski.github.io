# [Java][JVM][JIT] JDK 26 and SIMD operations

## SIMD - single instruction, multiple data

If you're already familiar with **SIMD** feel free to skip to next chapter. 

I believe everyone have a good feeling how Traditional (Scalar) Processing is working. CPU simply executes one
operation on one set of data, like ```a + b```. But what can we do to speed it up when we want to do same 
operation on multiple data sets? We can rely on CPU pipelining, out-of-order execution and superscalarity, but we
can go beyond that. That's the place where **SIMD** comes to play. 

Instead of doing one operation on one set of data we can put multiple data into _vectors_ and apply one instruction
on those. That's the whole magic.

## SIMD in Java

Java offers us two ways of using **SIMD** instructions:

- **JIT** optimization called **auto-vectorization**,
- **Vector API** that is still in incubation.

**JIT** part is great because our Java application can run faster without any additional work on programmer side. But 
can is produce code as good as we can do with **Vector API**? That's what we will test in this article.

## Simple synthetic example

Let's start with simple number adding: 

```java
@Benchmark
public int scalar() {
    int sum = 0;
    for (int i = 0; i < SIZE; i++) {
        sum += array[i];
    }
    return sum;
}
```

If we want to check if **auto-vectorization** was applied to our code and measure the speed-up, there is a simple trick.
You can disable that optimization with ```-XX:-UseSuperWord``` JVM flag. Comparing performance with and without the flag
gives you answers for those questions.

Benchmark results for ```scalar``` method on **M4 Max** CPU for array with size ```1_000_000```:

```
SumBenchmark.scalar                      avgt    6  113,049 ± 3,588  us/op
SumNoSIMDBenchmark.scalar                avgt    6  228,635 ± 2,849  us/op
```

**Auto-vectorization** speeds up the method **x2**. Great result, especially that we don't have to do anything
to get it. Let's now write same algorithm using **Vector API**. For simple algorithms it's easy task, for more 
complex one you can help yourself with AI, it's really good in transforming methods to **Vector API**.

```java
private static final VectorSpecies<Integer> SPECIES = IntVector.SPECIES_PREFERRED;

public int vectorApiOneAccumulator() {
    int lanes = SPECIES.length();
    int bound = SIZE - (SIZE % lanes);
    IntVector acc = IntVector.zero(SPECIES);
    for (int i = 0; i < bound; i += lanes) {
        acc = acc.add(IntVector.fromArray(SPECIES, array, i));
    }
    int sum = acc.reduceLanes(VectorOperators.ADD);
    for (int i = bound; i < SIZE; i++) {
        sum += array[i];
    }
    return sum;
}
```

The algorithm here is pretty straightforward. We have one accumulator: ```IntVector acc``` filled with zeros and we are adding
vectors that are part of the input array in the loop. In the end we need to add "leftovers" that didn't fit into
vector. The performance:

```
SumBenchmark.vectorApiOneAccumulator     avgt    6  113,832 ± 1,114  us/op
```

is the same as  **auto-vectorization** version, but can we get more?

If you look at the vector adding loop and unroll it:

```java
acc = acc.add(IntVector.fromArray(SPECIES, array, i));
acc = acc.add(IntVector.fromArray(SPECIES, array, i + lanes));
acc = acc.add(IntVector.fromArray(SPECIES, array, i + (2 * lanes)));
acc = acc.add(IntVector.fromArray(SPECIES, array, i + (3 * lanes)));
```

you can notice that CPU cannot speed it up more with its magic because we have data dependency here. Each line needs
a result from previous line to do its work. But nobody is forcing us to use only one accumulator, we can use more. Here
is an example with four accumulators:

```java
@Benchmark
public int vectorApiFourAccumulators() {
    int lanes = SPECIES.length();
    int step = lanes * 4;
    int bound = SIZE - (SIZE % step);
    IntVector v0 = IntVector.zero(SPECIES);
    IntVector v1 = IntVector.zero(SPECIES);
    IntVector v2 = IntVector.zero(SPECIES);
    IntVector v3 = IntVector.zero(SPECIES);
    for (int i = 0; i < bound; i += step) {
        v0 = v0.add(IntVector.fromArray(SPECIES, array, i));
        v1 = v1.add(IntVector.fromArray(SPECIES, array, i + lanes));
        v2 = v2.add(IntVector.fromArray(SPECIES, array, i + (2 * lanes)));
        v3 = v3.add(IntVector.fromArray(SPECIES, array, i + (3 * lanes)));
    }
    int sum = v0.add(v1).add(v2).add(v3).reduceLanes(VectorOperators.ADD);
    for (int i = bound; i < SIZE; i++) {
        sum += array[i];
    }
    return sum;
}
```

Simple idea, four accumulators adding parts of input array followed by sum over all accumulators and sum of leftovers.
Here are results for 2, 4, 8 accumulators:

```
SumBenchmark.vectorApiTwoAccumulators    avgt    6   56,954 ± 0,963  us/op
SumBenchmark.vectorApiFourAccumulators   avgt    6   34,653 ± 0,732  us/op
SumBenchmark.vectorApiEightAccumulators  avgt    6   34,307 ± 0,464  us/op
```

The speedups here are as follows:

- from 1 to 2 accumulators: **~x2**
- from 2 to 4: **~x1.65**
- from 4 to 8: **no speedup at all**

So with **Vector API** we can speed our algorithm by **~3.3**. Downsides? First of all it's not automatic, we need to
code it ourselves. Secondly: the **Vector API** version is far less readable than scalar one. This downside will be
even more visible in next chapter.

## Another example

This example is not synthetic at all. Some time ago I had to speedup an algorithm, where first part had to count
negative numbers in the array. The simple scalar code is easy:

```java
@Benchmark
public int branchy() {
    int negativeCount = 0;
    for (int v : array) {
        if (v < 0) {
            negativeCount++;
        }
    }
    return negativeCount;
}
```

Benchmark results for ```1_000_000``` random elements with _~50%_ of negative numbers: 

```
CountBenchmark.branchy                     avgt    6  231,072 ± 1,656  us/op
CountNoSIMDBenchmark.branchy               avgt    6  236,232 ± 2,184  us/op
```

**Auto-vectorization** cannot really help here, because we have a branch in our code. We need to get rid of it first and
figure out a branchless version of this algorithm. It's a good time to also recommend you great article written by 
Jaromir Hamala [The Most Expensive Instruction Might Be... cmov](https://questdb.com/blog/cmov-vs-branch-perf/){:target="_blank"} - great writting.

To make the above algorithm branchless we don't need ```cmov```. We just need one observation that every negative 
```int``` has its leftmost bit set to ```1```. So if we shift a number by ```31``` bits to the right we will get 
```1``` if number is negative and ```0``` if number is ```>= 0```. With that observation we can go with:

```java
@Benchmark
public int branchless() {
    int negativeCount = 0;
    for (int v : array) {
        negativeCount += v >>> 31;
    }
    return negativeCount;
}
```

Benchmark results:
```
CountBenchmark.branchless                  avgt    6  168,414 ± 0,250  us/op
CountNoSIMDBenchmark.branchless            avgt    6  228,633 ± 2,312  us/op
```

Nice speedup. If **auto-vectorization** can help it means that we also may try to write algorithm using **Vector API**.
Again, AI is a very good assistant here:

```java
@Benchmark
public int vectorApiOneAccumulator() {
    int[] array = this.array;
    int lanes = SPECIES.length();
    int bound = SIZE - (SIZE % lanes);
    IntVector acc = IntVector.zero(SPECIES);
    for (int i = 0; i < bound; i += lanes) {
        acc = acc.add(IntVector.fromArray(SPECIES, array, i).lanewise(VectorOperators.LSHR, 31));
    }
    int negativeCount = acc.reduceLanes(VectorOperators.ADD);
    for (int i = bound; i < SIZE; i++) {
        negativeCount += array[i] >>> 31;
    }
    return negativeCount;
}
```

The idea is very similar to previous example. We have one accumulator, we start with zeros and we add a part of input 
array shiffted by 31 bits. ```VectorOperators.LSHR``` here is vector equivalent to ```>>>``` opperation.

This algorithm have same flaw as previous single accumulator one - we have data dependency when we unroll the loop.
Same flaw, so same trick - multiple accumulators:

```java
@Benchmark
public int vectorApiFourAccumulators() {
    int[] array = this.array;
    int lanes = SPECIES.length();
    int step = lanes * 4;
    int bound = SIZE - (SIZE % step);
    IntVector v0 = IntVector.zero(SPECIES);
    IntVector v1 = IntVector.zero(SPECIES);
    IntVector v2 = IntVector.zero(SPECIES);
    IntVector v3 = IntVector.zero(SPECIES);
    for (int i = 0; i < bound; i += step) {
        v0 = v0.add(IntVector.fromArray(SPECIES, array, i).lanewise(VectorOperators.LSHR, 31));
        v1 = v1.add(IntVector.fromArray(SPECIES, array, i + lanes).lanewise(VectorOperators.LSHR, 31));
        v2 = v2.add(IntVector.fromArray(SPECIES, array, i + (2 * lanes)).lanewise(VectorOperators.LSHR, 31));
        v3 = v3.add(IntVector.fromArray(SPECIES, array, i + (3 * lanes)).lanewise(VectorOperators.LSHR, 31));
    }
    int negativeCount = v0.add(v1).add(v2).add(v3).reduceLanes(VectorOperators.ADD);
    for (int i = bound; i < SIZE; i++) {
        negativeCount += array[i] >>> 31;
    }
    return negativeCount;
}
```

Results:
```
CountBenchmark.vectorApiOneAccumulator     avgt    6  168,420 ± 0,403  us/op
CountBenchmark.vectorApiTwoAccumulators    avgt    6   84,183 ± 0,125  us/op
CountBenchmark.vectorApiFourAccumulators   avgt    6   43,338 ± 0,124  us/op
CountBenchmark.vectorApiEightAccumulators  avgt    6   34,263 ± 0,269  us/op
```

Overall speedup between **auto-vectorization** version and **Vector API** is up to **x4,95**.

## CPU matters

All those results are from my **M4 Max** machine. The speedup really depends on type of CPU you have and the size of 
vector registers. On my old ```i7-9850H``` results are completely different:

```
SumBenchmark.scalar                        avgt    6   54,964 ±  3,390  us/op
SumNoSIMDBenchmark.scalar                  avgt    6  228,140 ±  3,094  us/op

SumBenchmark.vectorApiOneAccumulator       avgt    6   57,408 ± 11,323  us/op
SumBenchmark.vectorApiTwoAccumulators      avgt    6   58,190 ±  7,644  us/op
SumBenchmark.vectorApiFourAccumulators     avgt    6   53,996 ±  3,135  us/op
SumBenchmark.vectorApiEightAccumulators    avgt    6   54,350 ±  2,284  us/op

CountBenchmark.branchy                     avgt    6  256,884 ±  6,028  us/op
CountNoSIMDBenchmark.branchy               avgt    6  262,384 ±  2,414  us/op

CountBenchmark.branchless                  avgt    6   57,695 ±  5,557  us/op
CountNoSIMDBenchmark.branchless            avgt    6  232,836 ±  4,617  us/op

CountBenchmark.vectorApiOneAccumulator     avgt    6   62,872 ± 21,866  us/op
CountBenchmark.vectorApiTwoAccumulators    avgt    6   53,855 ±  0,679  us/op
CountBenchmark.vectorApiFourAccumulators   avgt    6   60,530 ± 12,841  us/op
CountBenchmark.vectorApiEightAccumulators  avgt    6   57,576 ±  0,616  us/op
```

On this CPU there is a massive difference between **auto-vectorization** and scalar algorithms, and no difference
between single and multiple accumulators versions.
